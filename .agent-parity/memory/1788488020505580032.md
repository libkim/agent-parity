공유 MCP 매니페스트 기능의 설계 결정 4건과 근거(구현 시점에 내린 것, 재설계해도 유지할 판단). (1) 매니페스트 위치는 .agent-parity/mcp-servers.json — .agents/ 아래는 Antigravity가 mcp_config.json·hooks.json을 쓰는 디렉터리라 향후 규약 충돌 위험이 있고, .agent-parity/memory가 이미 "우리 네임스페이스 안의 사용자 소유 데이터" 선례를 만들었다. uninstall은 --purge 없이도 매니페스트를 남긴다(사용자 파일). (2) env 필드를 스키마에서 제외하고 모르는 키는 거부 — 이 파일은 메모리 저장소처럼 커밋되므로 API 키를 적으면 그대로 push된다. 비밀정보 거버넌스와 같은 위험이라 경고가 아니라 구조적으로 차단했다. 키가 필요한 서버는 한 에이전트 설정에 직접 등록하면 우리가 안 건드린다. (3) 소유권은 상태 파일로 증명 — 메모리 런처는 command 문자열로 우리 것임을 알아볼 수 있지만 사용자 서버의 command는 임의값이라 불가능하다. 실제로 등록한 이름을 기록해야 제거가 안전하고 수기 항목을 보호할 수 있다. 단 1차 구현은 상태를 전역으로 둬서 실패했고, 설정별로 기록해야 한다. (4) 사용자 서버는 등록만 하고 사전 승인하지 않는다 — 우리 메모리 서버는 우리가 만들어 배포하니 사전 승인이 정당하지만, 서드파티 서버의 도구를 4개 에이전트에서 한꺼번에 자동 허용하는 건 등록이 조용히 내릴 결정이 아니다. 나중에 넣는다면 매니페스트에 서버별 opt-in(preapprove) 형태가 안전하다. 범위 경계: 우리는 배선만 공유하고 설치는 안 한다(패키지 매니저 없음 원칙). 그래서 OS별 런처는 windowsCommand로 받는다.
